# DECISIONS — H3 本地加速

## D1. 用本地优化替代租 GPU（2026-10-21）

**决策**：不租 AutoDL，改走本地 h3.c 社区加速路线。

**理由**：
- M5 Pro 48GB 已能跑完整 H3（Metal 4 + 统一内存 + 原生 int8），出片质量与云端同源（同一份 BF16 权重）
- 本地零边际成本；云端 6000D ¥6.80/h、vGPU-32GB 包周 ¥262 / 包月 ¥867
- 只有"单日批量 20-30 条"这一个场景云端才更省（本地单条 12 分钟 vs 云端配 turbo 后 1-2 分钟）
- owner 明确倾向：本地有优化就直接本地省下 GPU 钱

**适用边界**：若单次批量 > 15 条或需在数小时内交付，再评估云端。

## D2. 选 Bambushu/integration 作为升级目标（2026-10-21）

**决策**：不选上游（已死），不选各个单点 fork，选 `Bambushu/h3.c` 的 `integration` 分支。

**理由**：
- 上游 `antirez/h3.c` 自 2026-08-11 零提交、29 个 PR 全未合
- integration 的 README 明确写"为 48GB M5 Pro 上的 9:16 生产镜头（0.5-1MP、5-15s、带语音）服务"，与本机场景完全重合
- 它基于 `jerryfane/community-integration`，后者在合入前逐个读过 PR 的恶意代码风险（网络/进程/文件写/构建规则/编码数据）
- 内含 `tools/fold_turbo_lora.py`（PR #14）、bf16 VAE（PR #73）、Sol-Attn、256px VAE 瓦片、DiT 加载缓存

## D3. 原环境不覆盖（2026-10-21）

**决策**：新分支只放 `~/h3c-build/h3-integration`，验证通过后才讨论是否切为主用。

**理由**：
- 原环境代码零改动（已核实 78 项状态均为文件权限位变化，insertions/deletions 均为 0）
- 权重 269G 不复制，新二进制直接读原路径验证通过
- integration 会改变同 seed 输出，切换有"既有调好的 prompt+seed 失效"的代价，需 owner 知情决定

### 审核给出的关键纠正

1. **风险不在"11 个 PR"，而在实际改动行数** —— 应读 `git diff`，不读 PR 描述。（已执行：8699 行插入）
2. **LoRA 反而是低风险项**：safetensors 是纯张量头，无反序列化执行；危险的格式是 pickle。LoRA 风险只是 shape/数值。
3. **seed 降级为"seed 家族"**：跨引擎逐帧对齐是不可能问题，不要尝试。
4. **Sol-Attn 最常见的失败模式不是画质差，而是运动幅度下降、变僵** —— 这比画质退化更难察觉，必须专门检查。
5. **hero 镜头走上游出**，文件名记 commit + seed + 引擎，否则三个月后不可复现。

## D6. Q4 切换判据（Opus 给定，采用）

3 条代表镜头（必须含带语音那条），预览分辨率跑，四条判据：

1. 无矩形马赛克 / 瓦片接缝（对应 256px 瓦片 + #70）
2. 唇形无明显漂移
3. 无逐帧闪烁 / 呼吸
4. **运动幅度未下降**（Sol-Attn 块稀疏最常见失败模式）

通过线：**3 条里 ≥2 条过 = 切**。任一出现马赛克或唇漂 = 不切，退回上游 F32 VAE，只留 bf16 VAE。

## D7. 云端切换阈值（Opus 给定，采用）

任一命中即切云：

1. 单片 >15 s 或 >1 MP（本地 >40 min/片，且 M5 长时间满载热降频，尾部退化）
2. 单日 >8 条成品（本地排队 >3 h）
3. 需并发 >2
4. prompt 探索 >10 轮/片（预览留本地，定稿一次性上云）

包月 ¥867 只在单月 ≥15 天满载时买；冲刺用包周 ¥262；按量 ¥6.80/h 只给"验证一条镜头值不值"的一次性任务。
