## 一、结论先行

**在本地跑 H3 视频生成，不需要租 GPU。** 社区已经把 antirez/h3.c 往前推了三个月，把一块 M5 Pro 48GB 的 768×1344 五秒片从 **27.7 分钟压到 20.5 分钟**，并且还有约 1.8 倍的组合空间没用上。

只有在「一天要出 20–30 条」这种批量场景下，云端才明显更便宜。

- **注意力是生产分辨率下的主要瓶颈**：1344×768/124 帧 = 37,296 token，去噪 36 分钟（M5 Max），时间基本花在等 MPSGraph

- **因此唯一的注意力杠杆是稀疏自定义内核（SolAttn / Veda / VSA）或蒸馏模型**

## 四、可用的加速手段（按性价比排序）

| # | 手段 | 效果 | 风险/代价 | 来源 |
|---|---|---|---|---|
| 1 | **bf16 视频 VAE 解码** | 解码 **3.2–3.8×**（M5 Pro 实测 170→45 s、264→82 s），画质 63 dB | 肉眼无差；`H3_VAE_PRECISION=f32` 可回退 | PR #73 |
| 2 | **折叠 Turbo LoRA** | 5–6 步采样，比 20 步快约 **1.35×** | 4 步有运动拖影；不可与 `--reuse` 同用；需下载适配器 | PR #14 + `tools/fold_turbo_lora.py` |
| 3 | **Sol-Attn 块稀疏注意力** | 去噪 **8%（0.5MP）/ 15%（1MP）**；内核本身快 12.7–22.6× | 输出是"另一条 take"，固定 seed 失效 | AlexanderIstomin → integration |
| 4 | **256px VAE 瓦片**（默认开） | 消除 16 像素网格伪影（grid score 1.81→1.10） | 解码慢约 14%，已被 bf16 抵消 | PR #1 |
| 5 | **VAE 解码流水线 + DiT 提前加载** | 字节一致，靠重叠省时 | 无 | jerryfane |
| 6 | **int8 权重替代 SSD 流式 BF16** | 下一步最大杠杆（约 2/3 步时耗在线性层） | 需移植 PR #55；48 GB 上偏紧 | 待做 |

### 4.1 关于 LoRA 的关键事实

**h3.c 没有 LoRA 运行时，也不需要**。做法是**离线折叠**：

```
W' = W + scale × (B @ A)
```

`tools/fold_turbo_lora.py` 用纯 numpy 直接改写 checkpoint 的字节区间，header、tensor 顺序、对齐全部保持字节一致。APFS 上每个折叠变体只占 2–3 GB 实际磁盘（写时复制）。

```bash
python3 tools/fold_turbo_lora.py \
  --checkpoint MiniMax-H3/FL2VA/transformer \
  --lora minimax_h3_turbo_v4_step600_ema.safetensors \
  --out MiniMax-H3-turbo/FL2VA/transformer
```

然后用 `--steps 5` 或 `6`。**4 步会出现运动拖影，5 步是下限。**

> 另注：运行时 LoRA 其实已被 5 个 fork 实现（neokree / LachlanStuart / JunzoKamahara / neysay / lyj97），但维护者判断"先放一放"，未进主分支。

### 4.2 关于 CFG 蒸馏的边界

Turbo LoRA 减的是**采样步数**，不是模型体积。底座权重仍需 19.5 G（pruned fp8）或流式 BF16 62 G。它让 VAE 之外的时间大幅缩短，但不改变显存峰值（峰值由权重驻留决定）。

### 本机 A/B 实测（冒烟规模：512×512 / 22 帧 / 6 步 / 45 层）

| 配置 | DiT total | video VAE | 后段合计 |
|---|---|---|---|
| 上游 8974cc0（F32 VAE） | 130.128 s | 26.131 s（独立） | **156.3 s** |
| integration，预取 ON | 153.724 s | 6.097 s（流水线） | 159.8 s |
| integration，预取 OFF | 135.322 s | 23.210 s（独立） | **158.5 s** |

**冒烟规模下集成版没有优势（慢约 2%）。**

### 但根因已定位，且不可外推

去噪回归来自 **VAE 预取抢 GPU**：`H3_VAE_PREFETCH=0` 后去噪从 22.97 s 回到 **12.99 s**（上游 13.31 s，差异是噪声）。

关键在于**成本结构不同**：

- 预取是**固定成本**约 10 s（加载 4.8 GiB 解码器），不随片长增长
- VAE 收益**随片长放大**：冒烟规模只省 3 s，生产规模省 180+ s

所以：
- 预览/小片（≤32 帧、≤640²）→ `H3_VAE_PREFETCH=0`
- 生产片（≥100 帧、≥768×1344）→ 保持预取，净赚

### 尚未完成（升级决策前必做）

- **生产规模本机 A/B**（768×1344 / 124 帧 / 8 步）：社区在同型机报 1.35×，但那是他机数据
- Turbo LoRA 下载与折叠验证（适配器 744 MB，`larryvrh/MiniMax-H3-Turbo-Lora` 的 `minimax_h3_turbo_v4_step600_ema.safetensors`）

### 中间点实验（Opus P0-2，已完成）

参数：768×1344 / 49 帧（实出 56 帧 / 2.333 s）/ 8 步 / 50 层 / seed 42

| 阶段 | 预取 ON | 预取 OFF | 差值 |
|---|---|---|---|
| Qwen 文本编码 | 77.058 s | 77.180 s | ≈0 |
| DiT 加载 | 128.053 s | 128.208 s | ≈0 |
| **GPU Euler 去噪** | **465.277 s** | **480.415 s** | **ON 快 15.1 s** |
| DiT total | 598.566 s | 609.030 s | ON 快 10.5 s |
| **video VAE 解码（关键路径）** | **74.047 s** | **102.013 s** | **ON 快 28.0 s** |
| output tail | 84.877 s | 104.560 s | ON 快 19.7 s |
| **后段合计** | **683.4 s** | **713.6 s** | **ON 快 30.2 s（−4.2%）** |

**画面一致性（强证据）**：ON 与 OFF 逐帧比对，全部 56 帧 `psnr_avg:inf`、`mse_avg:0.00`，帧哈希完全相同（`0845e442…`）。**预取只改时序，不改像素。**

**结论**：预取成本固定（4.8 GiB 解码器加载），收益随解码工作量放大。交叉点在 512²/22 帧与 768×1344/49 帧之间。

策略：
- 预览/小片（≤32 帧、≤640²）→ `H3_VAE_PREFETCH=0`
- 中间点及以上（≥49 帧或 ≥768×1344）→ **保持预取默认开启**

目检：768×1344 首帧（人物面部 + 大量发丝）无矩形马赛克、无瓦片接缝、发丝细节完整，未复现社区普查中的 #70 缺陷。

## 七、必须知道的代价
1. **integration 在相同 seed 下与上游输出不一致。** 已知会改输出的至少有一项（PR #63 的 GQA 竞态修复）。升级后既有调好的 prompt+seed 组合会变，要重新挑一轮片。
2. **Sol-Attn 换内核后固定 seed 失效**，输出是"另一条 take"而不是"更差的 take"。得按画面本身评判。
3. **折叠 Turbo LoRA 不可与 `--reuse` 同用**（蒸馏调度已去掉了那部分冗余）。
4. **h3.c 与 ComfyUI 两条路互不相通**：`H3Local` 节点走 h3.c，官方 MiniMaxH3 节点走 torch，前者在 MPS 上有专用优化，后者依赖 `aten::_int_mm`（MPS 不支持，官方节点在 Mac 上直接失败）。

### Q1 升级路径 → 走 integration，vpipe 仅备用

采纳理由（Opus）：
- vpipe 虽是独立 C++/Metal 重写、更快且修了 #70，但**会让 ComfyUI-H3Local 的 shell 调用链路失效**，需重写集成层。为增量速度做这种改造成本不划算
- vpipe 没有 LoRA 折叠；integration 的 `fold_turbo_lora.py` 才是 5–6 步采样的前提，**省下的是采样步数，收益大于 vpipe 的 kernel 优势**
- 不升级不可行：本地省钱这个论点，靠的就是 27.7min→20.5min
- **若 #70 马赛克确实出现在某条具体镜头（浓密毛发/高频布料），把 vpipe 作为那条镜头的备用，不走主路径**

### Q2 预取推断 → 成立，但必须先跑中间点

Opus 修正了我的机制描述：
- 预取成本 = 4.8 GiB 解码器权重加载争抢带宽，**加载量固定 → 成本固定** ✓
- VAE 收益分两块：bf16 解码本身（**随像素数增长**）和把加载移出关键路径（**固定**）
- **交叉点 = 解码工作量 > 加载工作量**。512²×22 帧正好在交叉点附近，所以净亏 1.3 s，与实测吻合
- 他机数据是直接证据：同型 M5 Pro 48GB，生产规模去噪 1272 s < 上游 1375 s，预取惩罚消失
- **但必须先跑中间点（768×1344 / 49 帧，ON/OFF 各一次）再定默认值**。中间点 ON 不亏，策略即可上线
- **只认 wall clock 总时长，分段计时会骗人**

### Q3 供应链 → 中风险可接受，须满足 4 条件

Opus 的关键纠正：**风险不在"11 个 PR"，而在实际改动行数**——应读 `git diff`，不读 PR 描述。

已执行审计（详见 `.task/AUDIT.md`）：`47 files changed, 8699 insertions(+), 604 deletions(-)`。
四类恶意行为 grep 结果：**网络出站零命中、敏感路径零命中、混淆仅终端 base64、进程调用仅 ffmpeg**。

Opus 指出的一个反直觉点：**LoRA 反而是低风险项**——safetensors 是纯张量头，无反序列化执行；危险的是 pickle 格式。LoRA 风险只是 shape/数值。

四个缓解条件：
1. pin `8e682e8` 并 vendor 进仓库，永不 `git pull`
2. 沙箱用户跑，主账号（带 SSH key、云凭据）不碰
3. `sandbox-exec` 挡网络出站 + 只许写 output 目录
4. h3.c 二进制与 LoRA 的 sha256 进构建脚本

最小替代（若风险不接受）：**只 cherry-pick PR#73（bf16 视频 VAE 解码）**，单它就有 3.2× VAE 加速，diff 最小可审计。

### Q4 seed 变化 → 三镜头阶梯，不做全量 A/B

- **seed 降级为"seed 家族"**：跨引擎逐帧对齐是不可能问题，别尝试
- 固定 3 条代表镜头（**带语音那条必须在内**），预览分辨率跑
- 四条判据：① 无矩形马赛克/瓦片接缝 ② 唇形无明显漂移 ③ 无逐帧闪烁/呼吸 ④ **运动幅度未下降**（Sol-Attn 块稀疏最常见失败模式是运动变小变僵，比画质退化更难察觉）
- 通过线：**3 条里 ≥2 条过 = 切**；任一出现马赛克或唇漂 = 不切，退回上游 F32 VAE，只留 bf16 VAE
- hero 镜头走上游出，文件名记 commit + seed + 引擎，否则三个月后不可复现

### Q5 本地 vs 云端 → 结论成立，有明确阈值

- 本地 ~100 W ≈ ¥0.06/h，可忽略。**本地永远赢现金；云端买的不是算力，是时间**
- 本地 23.6 min / 5.17 s 输出 ≈ 4.6 计算分/输出秒
- 任一命中即切云：
  1. 单片 >15 s 或 >1 MP（本地 >40 min/片，且 M5 长时间满载热降频，尾部退化）
  2. 单日 >8 条成品（本地排队 >3 h）
  3. 需并发 >2
  4. prompt 探索 >10 轮/片（预览留本地，定稿一次性上云）
- 包月 ¥867 只在单月 ≥15 天满载时买；冲刺用包周 ¥262；按量 ¥6.80/h 只给"验证一条镜头值不值"的一次性任务
- **日更 = 云**（本地 20.5 min/条撑不住）
